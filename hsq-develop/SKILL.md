# HSQ Develop

## 目标

按用户偏好的完整工程闭环工作：理解上下文，识别任务模式，定位根因或设计边界，实施最小且完整的修改，验证结果，并说明剩余风险。保持项目现有框架、目录结构、工具和编码习惯。

## 模式识别

根据用户意图自动选择流程：

- **排查、为什么、是否有问题、卡顿、失败**：进入诊断流程。
- **实现、修改、优化、支持、修复**：进入实现流程。
- **检查、review、有没有问题、未提交代码**：进入审查流程。
- **合并、拉取、提交、同步分支**：进入 Git 流程。
- **部署、容器、K8s、登录失败**：进入部署诊断流程，并与诊断或性能流程组合。
- **慢、性能、缓存、耗时**：建立量化基线后进入性能流程。
- **方案、设计、默认值、字段、接口**：先分析契约和兼容性；用户只要求方案时不要直接改代码。

## 每项任务先做

1. 阅读仓库级 `AGENTS.md`、README、相关设计文档和测试入口；遵守其更具体的规则。
2. 检查 `git status`、当前分支、基线和已有 staged、unstaged、untracked 改动；绝不覆盖用户已有修改。
3. 识别技术栈、运行环境、配置来源、构建/测试/lint 命令和外部依赖。
4. 把用户目标转成可验证的行为、边界和验收条件；在 commentary 中简要说明当前模式和检查范围。
5. 使用 `rg`、结构化解析、调用链、日志、测试或基准获取证据，不凭文件名或直觉猜测。

## 诊断流程

1. 尽量建立可重复的最小复现；不能复现时明确记录观测证据和限制。
2. 沿数据流、控制流、事件时序和持久化边界追踪；对异步问题检查重复订阅、丢事件、乱序、重试、幂等和刷新/恢复路径。
3. 为每个假设指定可证伪的检查，区分直接根因、放大因素、相关风险和无关现象。
4. 明确区分“后端/数据真的丢失”和“前端/UI 暂时未显示”，区分“接口慢”和“调用方重复工作”。
5. 用户只要求诊断或分析时保持只读，不修改代码、不发送业务请求、不改变远端数据。
6. 输出问题结论、证据、因果链、影响范围、推荐修复边界和未确认事项。

## 实现流程

1. 先定位入口、状态/数据模型、所有消费者和现有测试；不要只改报错行。
2. 分析影响面：其他接口和 tool、共享模块、并发/异步路径、UI、日志、部署配置、历史数据和文档契约。
3. 检查兼容性：旧用户升级、旧配置、旧数据、默认值、创建与更新语义、可选与必填字段、失败时是否会出现“保存成功但不可用”。
4. 非平凡改动先给出简短方案、风险和测试计划；用户明确要求实施时继续完成，不停在建议阶段。
5. 实施最小的连贯修改：修复根因，不用固定延时、无界重试、扩大查询、字符串猜测或其他掩盖竞态的办法替代设计修复。
6. 保留既有接口和内部调用方需要的元数据；面向模型的业务结果与日志/诊断信息分层，避免二次序列化破坏结构化消费。
7. 对状态机和流式功能验证终态、取消、拒绝、超时、重连、重复事件、乱序事件和持久化/UI 一致性。
8. 执行最相关的单元/集成测试、类型检查、构建或 lint；必要时补回归测试。报告实际执行的命令和结果。
9. Bug 修复完成后，针对同一根因、反模式、共享 helper/状态机或复制代码做轻量横向搜索。发现可能存在类似 Bug 的候选位置时，在交付总结中说明证据和可能范围，并询问用户是否继续专项检查；未经确认不要把额外修复混入当前任务。

## 性能流程

1. 先定义指标和基线，例如响应时间、吞吐、内存、渲染耗时或每帧预算。
2. 使用真实或接近真实的数据量复现；定位调用链、重复扫描、序列化、I/O、数据库锁、缓存命中率和前端重渲染。
3. 用隔离实验验证主因，再做最小优化；优化前后使用同一条件重新测量。
4. 不以“可能更快”作为结论；没有可靠基线时明确标注推测和下一步测量计划。

## 代码审查流程

1. 明确审查基线，默认检查 `HEAD` 相对工作区的 staged、unstaged 和 untracked 内容。
2. 先报告按严重度排序的可操作问题，并附文件和行号；重点检查功能回归、安全/敏感信息、兼容性、并发状态、配置契约、测试隔离和范围混杂。
3. 检查测试是否真正执行行为，而不是只匹配源码字符串；注意干净 checkout、被忽略构建产物和生成文件依赖。
4. 没有发现问题时明确说明，并列出剩余测试缺口或残余风险；除非用户要求，否则审查不直接修改文件。

## Git 与交付流程

1. 拉取、合并或提交前先检查工作区、分支、上游和远端差异；保留与当前任务无关的用户改动。
2. 按用户指定的业务优先级处理冲突；复杂、语义冲突或无法判断的冲突先暂停询问，不擅自选择。
3. 提交前检查 diff、敏感信息、`git diff --check` 和相关测试；只有用户明确要求时才 commit、push 或改变远端分支。
4. 交付总结包含：改动目标、关键文件、行为变化、验证命令/结果、配置或部署注意事项、兼容性和剩余风险。

## 部署与外部环境

1. 先只读收集客户/容器/K8s 的版本、镜像、env、挂载、权限、网络、探针、日志和资源限制，与本地成功环境逐项对比。
2. 区分应用代码错误、配置缺失、镜像差异、运行时差异、存储权限、网络依赖和数据问题；建立最小复现后再提出修改。
3. 默认不重启生产服务、不删除数据、不改远端配置、不发送业务写请求；需要这些操作时先说明目标、影响和回滚方式并获得授权。

## 统一检查清单

在完成前回答：

- 根因是什么，证据在哪里，哪些只是放大因素？
- 影响哪些其他功能、tool、消费者、租户或部署环境？
- 旧用户、旧数据、旧配置和默认值是否仍然可用？
- 是否存在并发、重复、乱序、重试、取消或刷新后的状态问题？
- 性能结论是否有基线和前后对照？
- 测试是否覆盖行为、失败路径和回归场景？
- 本次 Bug 的根因是否可能在其他路径重复出现？如有候选，是否已提醒用户决定要不要继续检查？
- 是否需要更新契约文档或 Wiki？

## 暂停条件

遇到破坏性操作、生产环境写入、凭据/权限变更、复杂业务冲突、无法判断的兼容性取舍或新增高风险默认值时先暂停确认。其他情况下保持自主推进，直到完成验证和交付总结。
