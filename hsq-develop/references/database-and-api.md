# Database and API

## SQL Guardrails

1. 未经用户明确同意，不使用窗口函数。需要使用时，先说明必要性、数据库兼容性、性能影响以及可选替代方案，再等待确认。
2. 未经用户明确确认，不创建唯一索引，不新增表字段。提出此类变更时，先说明业务约束、影响范围、存量数据兼容性、迁移与回滚方式以及替代方案。
3. 查询 SQL 必须同时验证结果正确性和性能。结合实际数据规模评估过滤条件、索引利用、扫描范围、Join、排序、聚合、分页、返回数据量和数据库往返；性能敏感查询应检查执行计划或等价证据。
4. 没有执行计划、基准或真实数据量证据时，不把性能判断表述为已验证结论，明确剩余风险和验证方式。

## Backend API Query Strategy

1. 尽量减少高耗时 SQL、不必要的重复查询和数据库往返，主动检查 N+1 查询以及依赖前序结果的线性查询链。
2. 在保证业务语义、数据一致性、可维护性和查询性能的前提下，优先将查询设计为可独立执行、批量获取或并行组织，避免多个 SQL 串行累积接口延迟。
3. 独立查询优先不是强制拆分，也不等于追求最少 SQL 数量。不要为了减少查询次数强行合并成复杂大查询；根据数据量、索引、锁竞争、网络往返、事务边界和执行计划选择方案。
4. 设计或修改 API 后台逻辑时，说明查询次数、查询依赖、批量边界、失败语义和一致性要求。性能敏感改动应以执行计划、查询耗时、扫描行数或接口前后指标验证。
