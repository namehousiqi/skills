# Implementation and Verification

## First-Principles Feature Design

功能开发时按任务风险选择必要深度：

1. 先定义用户要获得的可观察结果和验收条件，不把页面、字段、接口或当前实现方式误当成需求本身。
2. 区分业务事实、硬约束、系统不变量、历史实现惯例和未验证假设；优先验证会改变设计的关键假设。
3. 从事实和约束推导完成目标所需的最小领域模型、状态归属、权威数据源、状态转换、失败语义和必要接口。
4. 再将推导结果映射到现有架构，优先复用成熟能力并保持兼容；第一性原理不等于忽略项目约定、重造框架或扩大范围。
5. 方案必须能说明“为何这些机制足够、为何更少不够”，并用行为测试验证推导出的不变量和验收条件。

## Validate Spec Preconditions

1. 实施前提取 Spec、需求或设计文档中关于现有系统的关键陈述，包括当前行为、数据来源、状态归属、接口契约、依赖关系和 Bug 根因。
2. 使用代码、配置、测试、调用链或运行结果验证会影响实现方向的关键前提；文档中的原因判断只作为待验证假设。
3. 区分实质冲突与无关差异。命名、代码组织或省略的内部细节不同，但行为、约束和契约一致时可以继续。
4. 如果差异可能影响目标、验收标准、修改位置、数据模型、兼容性、接口契约、Bug 根因或修改是否必要，立即停止当前任务的写入和后续步骤。
5. 向用户说明文档中的预期、代码中的实际行为、支持结论的证据、对当前方案的影响和可选择的处理方向。
6. 用户明确选择以文档、当前实现或更新后的需求为准后再继续。等待期间只进行帮助用户判断的只读调查，不自行纠正文档、代码或需求。

## Design the Change

1. 定位入口、状态/数据模型、所有消费者和现有测试，不要只改报错行。
2. 分析其他接口和 tool、共享模块、并发路径、UI、日志、运行配置、历史数据和文档契约的影响。
3. 检查旧用户升级、旧配置、旧数据、默认值、创建/更新语义、可选/必填字段，避免“保存成功但不可用”。
4. 非平凡或高风险改动先说明简短方案、风险和测试计划；用户要求实施后继续完成。

## Implement and Verify

先复用当前会话中已经完成且范围未变化、证据仍有效的检查，只补做未覆盖或新增要求的校验；不要因加载技能或进入交付阶段而机械重跑等价检查。

1. 实施能够满足验收条件或恢复不变量的最小连贯改动；Bug 修复优先落在最低稳定责任边界。不要用固定延时、无界重试、扩大查询或字符串猜测掩盖设计问题。
2. 保留既有接口和内部调用方需要的元数据；将模型可见业务结果与日志/诊断信息分层，避免二次序列化。
3. 对状态机和流式功能验证终态、取消、拒绝、超时、重连、重复/乱序事件和持久化/UI 一致性。
4. 执行相关单元/集成测试、类型检查、构建或 lint；必要时补回归测试并报告实际结果。

## Check Adjacent Bugs

Bug 修复后，针对相同根因、反模式、共享 helper/状态机或复制代码做轻量横向搜索。发现候选类似 Bug 时说明证据和范围，并询问用户是否继续专项检查；未经确认不要把额外修复混入当前任务。

## Offer ego-browser Verification

1. 界面或前端交互调整完成，或任务需要浏览器自动化测试时，检查当前 agent 的可用 skill 列表是否包含 `ego-browser`。
2. 已安装且用户尚未指定验证工具时，提醒用户并询问是否使用；得到确认后再调用。
3. 用户已明确要求使用时直接按该 skill 验证，不重复询问。未安装时不声称可用，也不阻塞其他验证方式。
4. 执行后覆盖受影响主流程、关键交互、错误状态及必要的桌面/移动视口，并报告验证证据。
