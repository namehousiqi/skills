# Diagnosis and Performance

## First-Principles Bug Analysis

1. 先定义可观察的预期行为、实际行为和触发条件，不从报错位置或现有实现直接假定根因。
2. 区分已验证事实、业务硬约束、系统必须保持的不变量、历史惯例和未验证假设；主动验证会改变结论的假设。
3. 沿输入、状态转换、事件时序和依赖边界反向追踪，找到最早被破坏的不变量；把后续报错和异常 UI 视为症状候选。
4. 用“触发条件 -> 首个违规点 -> 状态或数据传播 -> 用户可见症状”描述因果链，并为关键环节提供可证伪证据。
5. 将修复放在能够恢复不变量的最低稳定责任边界。只有证明该边界不可修改时才采用上层补偿，并明确其局限。

## Diagnose with Evidence

1. 尽量建立可重复的最小复现；不能复现时记录观测证据和限制。
2. 沿数据流、控制流、事件时序和持久化边界追踪。对异步问题检查重复订阅、丢事件、乱序、重试、幂等和刷新恢复。
3. 为假设指定可证伪检查，区分直接根因、放大因素、相关风险和无关现象。
4. 区分数据真的丢失与 UI 暂时未显示，区分接口本身慢与调用方重复工作。
5. 只要求诊断时保持只读。输出结论、证据、因果链、影响范围、修复边界和未确认事项。

## Measure Performance

1. 先定义响应时间、吞吐、内存、渲染耗时或帧预算等指标，并记录基线。
2. 使用真实或接近真实的数据量复现，定位重复扫描、序列化、I/O、数据库锁、缓存和前端重渲染。
3. 用隔离实验验证主因，再做最小优化；在相同条件下重新测量。
4. 不以“可能更快”作为结论。没有可靠基线时标注推测和下一步测量计划。
